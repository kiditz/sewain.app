# Backend and frontend security review

**Follow-up:** patches and regression results are available in the [remediation report](remediation-2026-11-06.md). The findings below preserve the state observed during the initial review.

Date: November 6, 2026. Scope: authentication, object/tenant authorization, public catalog, cart/checkout, media uploads, and storefront rendering in the working tree at review time.

**Results: 7 findings — 5 high priority (P1), 2 medium priority (P2).** This was a source review with one local renderer reproduction, not a penetration test or a claim that production is secure or has been exploited. No migration endpoints, transactions, or malicious payloads were executed. No application code was changed for this review.

| ID | Priority | Area | Finding |
|---|---|---|---|
| SEC-01 | P1 | Backend | Merchant updates do not check object ownership and transfer the owner to the caller |
| SEC-02 | P1 | Backend | All-tenant migrations can be invoked without authentication |
| SEC-03 | P1 | Backend | Cart trusts customer IDs from a public header |
| SEC-04 | P1 | Backend | Public product APIs expose drafts and internal inventory fields |
| SEC-05 | P1 | Frontend/backend | Stored XSS in storefront rich text and block labels |
| SEC-06 | P2 | Backend | Upload validation trusts request MIME and preserves active extensions |
| SEC-07 | P2 | Frontend/backend | Button/Logo URL protocols are not filtered during rendering |

## SEC-01 — Cross-owner merchant updates

**Evidence:** [MerchantCommandServiceImpl.java](../../backend/src/main/java/app/sewain/merchants/MerchantCommandServiceImpl.java#L46), [controller](../../backend/src/main/java/app/sewain/merchants/MerchantCommandController.java#L27).

`PUT /api/merchants/{id}` takes a user ID from the token, then the service calls `merchantRepository.findById(merchantId)` without an owner predicate or a membership/role check on the target merchant. After mapping changes, it calls `merchant.setUserId(userId)`.

A logged-in account that knows another merchant's ID can change that merchant's name, slug, publication status, domain, and business information while transferring `user_id` to itself. This can remove the merchant from the original owner's `findByUserId` results after the cache expires. This is not proof of full access to the tenant database: the `merchant_users` membership table is not transferred through this path.

TenantFilter does not close this object-level gap: it checks membership for the request tenant, not the merchant targeted by `{id}`. Requests using the public context or the caller's own tenant can still reach the target object lookup. The Merchant entity itself maps to the `public` schema.

**Fix:** look up merchants by ID and authorized principal, or validate the role on the target ID before mapping. Do not change `userId` during ordinary profile updates. Ownership transfer must be a dedicated operation with its own rules.

**Required regressions:** user A cannot update merchant B, either without a tenant header or using tenant A; return 403/404 and keep all B metadata/ownership unchanged. Updating one's own merchant must not implicitly change ownership.

## SEC-02 — Public migration endpoint

**Evidence:** [SecurityConfig.java](../../backend/src/main/java/app/sewain/config/SecurityConfig.java#L44), [MerchantCommandController.java](../../backend/src/main/java/app/sewain/merchants/MerchantCommandController.java#L33), [MerchantSchemaService.java](../../backend/src/main/java/app/sewain/merchants/MerchantSchemaService.java#L49).

`/api/merchants/migrate` is included in `permitAll`. Its controller method checks no principal/role and calls `migrateAllTenantSchemas()`, which runs Flyway for every merchant schema.

Anonymous callers can trigger cross-tenant database work, execute pending migrations, and repeatedly run migration work that loads the database. Impact may include locks and availability disruption. Even without pending migrations, requests enter the workflow for every schema. This endpoint was deliberately not invoked during the review.

**Fix:** remove this operation from the public API. Prefer an internal deployment job/CLI. If retaining an endpoint, restrict it to platform operators and add auditing, concurrent-execution prevention, and network controls. An ordinary merchant owner role is insufficient for an all-tenant operation.

**Regressions:** reject anonymous requests and ordinary merchant accounts before invoking the service; only platform operators may run the job.

## SEC-03 — Customer-cart IDOR

**Evidence:** [CartController.java](../../backend/src/main/java/app/sewain/orders/CartController.java#L17), [CartServiceImpl.java](../../backend/src/main/java/app/sewain/orders/CartServiceImpl.java#L125), [SecurityConfig.java](../../backend/src/main/java/app/sewain/config/SecurityConfig.java#L52).

All `/api/cart/**` routes are public. `X-Customer-Id` directly determines cart identity. The service calls `findByCustomerIdAndStatus` without binding that customer to a logged-in identity. `validateOwner` only ensures that exactly one of customer ID or guest token is supplied; that is not an ownership check.

Given a known customer UUID in the target tenant, an anonymous caller can read the cart and change/delete its items. Hard-to-guess UUIDs limit discovery but do not provide authorization.

Additionally, `getCart` does not call `validateOwner`. A GET without either header reaches a guest-token lookup with a null value. Spring Data derived queries can translate a null parameter into `IS NULL`; if customer-owned carts have null guest tokens, results depend on the data and may expose a cart or cause a non-unique result error. This path was not tested against a database.

**Fix:** derive customer IDs from a verified customer session/token. Until customer login is available, reject `X-Customer-Id` on anonymous APIs and use random guest tokens as capabilities. Require owner validation on GET as well. Every operation must use a server-resolved owner.

**Regressions:** missing identity, forged customer headers, or another customer's identity must not allow cart reads/changes; legitimate owners and valid guest tokens must retain access to their own carts.

## SEC-04 — Public catalog uses the admin data model

**Evidence:** [SecurityConfig.java](../../backend/src/main/java/app/sewain/config/SecurityConfig.java#L48), [ProductQueryServiceImpl.java](../../backend/src/main/java/app/sewain/catalogs/ProductQueryServiceImpl.java#L32), [ProductVariantResponse.java](../../backend/src/main/java/app/sewain/catalogs/ProductVariantResponse.java#L8), [InventoryUnitResponse.java](../../backend/src/main/java/app/sewain/catalogs/InventoryUnitResponse.java#L6).

Product GET endpoints are public, but searches use request filters without enforcing public status. Callers can omit status or request `status=DRAFT`. ID and slug lookups also do not check public status.

The same response is used for administrators and visitors. Variants include `buyPrice` and `inventoryUnits`; inventory units include barcodes, serial numbers, status, and condition notes. The mapper does not redact these fields. Visitors can retrieve draft products and their operational details when data exists. A frontend composable's `status: ACTIVE` filter controls the UI, not the API security boundary.

**Fix:** separate public queries/DTOs from merchant queries/DTOs. Public queries must enforce server-side visibility rules; public DTOs must omit purchase prices, physical unit lists, serial numbers, and internal notes. Define UNLISTED policy explicitly: intentional detail access does not imply inclusion in public search. Administrators should retain draft access through protected endpoints.

**Regressions:** anonymous callers cannot retrieve drafts through search, ID, or slug; internal fields must be absent from public JSON, including for ACTIVE products.

## SEC-05 — Stored XSS in storefront HTML

**Evidence:** [TextBlock.vue](../../web/app/features/storefront-builder/components/blocks/TextBlock.vue#L53), [HeadingBlock.vue](../../web/app/features/storefront-builder/components/blocks/HeadingBlock.vue#L44), [EyebrowBlock.vue](../../web/app/features/storefront-builder/components/blocks/EyebrowBlock.vue#L43), [BlockLabel.vue](../../web/app/features/storefront-builder/components/blocks/BlockLabel.vue#L5), [ThemeLibraryService.java](../../backend/src/main/java/app/sewain/storefront/ThemeLibraryService.java#L258).

Text, Heading, and Eyebrow insert strings into `v-html` without sanitization. BlockLabel only checks whether a string contains one of several rich-text tags; if so, it returns the entire string unchanged. A `<p>` tag is therefore enough to pass through other active tags/attributes. Product descriptions also reach HTML rendering. The backend validates theme JSON structure but not HTML within settings; product descriptions are unrestricted strings.

**Local reproduction performed:** BlockLabel was compiled with the Vue compiler and rendered with Vue SSR in Node. The following inert input preserved its `onerror` attribute in the output:

```html
<p>security-review</p><img src="x" onerror="/* review-marker */">
```

Check result: `renderedEventAttributeUnchanged: true`. No malicious JavaScript was executed. The reproduction proves that HTML is not sanitized; browser execution impact is inferred from the use of `v-html`, not from a browser exploit performed during this review.

Imported theme JSON and stored content can reach merchant previews and public storefronts. Quill/toolbars are not a trust boundary because requests/imports can bypass the editor. If a merchant opens this content on the dashboard's origin, risks include bearer-token theft: [useAuth.ts](../../web/app/composables/useAuth.ts#L8) stores the access token in a JavaScript-readable cookie.

**Fix:** use a parser-based sanitizer with allowlisted elements, attributes, and protocols matching the rich-text format. Apply it to writes/imports and rendering to protect legacy data. Remove event handlers, active elements, dangerous URLs, and unnecessary style attributes. A tag-detection regex is not a sanitizer. Add a Nuxt-compatible CSP as defense in depth, not as a sanitizer replacement.

**Regressions:** valid rich text still renders, while event handlers, active markup, and dangerous-protocol links are rejected/sanitized in editor previews and public pages. Tests must cover imports, direct API input, and legacy data.

## SEC-06 — Active file uploads with forged MIME

**Evidence:** [MediaCommandServiceImpl.java](../../backend/src/main/java/app/sewain/media/MediaCommandServiceImpl.java#L105), [MIME check](../../backend/src/main/java/app/sewain/media/MediaCommandServiceImpl.java#L166), [extension](../../backend/src/main/java/app/sewain/media/MediaCommandServiceImpl.java#L190), [MediaWebConfiguration.java](../../backend/src/main/java/app/sewain/media/MediaWebConfiguration.java#L18).

Normal uploads only check for nonempty content and a multipart Content-Type starting with `image/`. The caller controls this value. The original filename extension is retained and the file is exposed through a public resource handler. An HTML file named `.html` with multipart MIME `image/png` can pass validation; active SVG also falls under `image/*`. The resource resolver only treats PNG signatures specially rather than sanitizing all uploads.

This permits hosting active content on the media provider's origin when a file is opened as a document. Frontend session impact depends on whether media and application origins/hosts/cookies share a trust boundary in deployment. Loading an SVG inside `<img>` is not itself equated with script execution; the risk here is direct navigation or active-document embedding. No test file was uploaded during the review.

**Fix:** allowlist required raster formats, verify them through a decoder, bound dimensions/decompression, and derive extensions/MIME from verified or re-encoded content. If SVG is required, use a dedicated sanitization policy or rasterization. Serve user content from an origin without application cookies, use appropriate response headers, and restrict the resource handler to a media prefix.

**Regressions:** reject MIME/extension/content mismatches, HTML labeled as an image, and active SVG; valid raster uploads and background-removal replacements must still work. Existing multipart limits of 5 MB/file and 20 MB/request do not replace format validation.

## SEC-07 — Raw block URLs reach href attributes

**Evidence:** [ButtonBlock.vue](../../web/app/features/storefront-builder/components/blocks/ButtonBlock.vue#L22), [LogoBlock.vue](../../web/app/features/storefront-builder/components/blocks/LogoBlock.vue#L38). Existing protocol-restricted examples: [PolicyLinkBlock.vue](../../web/app/features/storefront-builder/components/blocks/PolicyLinkBlock.vue#L9), [social-links.ts](../../web/app/features/storefront-builder/utils/social-links.ts#L16).

Button and Logo use stored URLs directly as href values. Theme structure validation does not filter protocols in block settings. The editor's link picker constrains normal input but does not constrain imported JSON, direct APIs, or legacy data. A `javascript:` URL can enable execution when a user clicks it, even after rich-text sanitization is fixed.

**Fix:** use a shared URL resolver in the backend and renderer. Prefer stored refs/targets for internal links; allow only supported protocols for external URLs. Canonicalize before protocol checks and handle control characters. Legacy/imported data must follow the same rules. Image URLs and navigation URLs are different policies.

**Regressions:** valid internal and HTTPS navigation still works; `javascript:`, `data:`, capitalization/control-character variants, and disallowed protocol-relative URLs must not become active href values.

## Hardening gaps and items requiring confirmation

The following are separate from the seven main findings because some impact depends on policy or infrastructure:

- **Merchant roles are not enforced.** MerchantRole defines OWNER/ADMIN/MEMBER, but TenantAccessService checks only membership and sensitive APIs have no role guards. Define an access matrix before treating MEMBER as an administrator. Pay particular attention to payment settings, finance, customer data, and theme publication.
- **Fail-open tenants and reserved slugs.** Unknown slugs fall back to `public`; the public schema bypasses membership checks. Slug validation accepts `public`. Separate global routing from tenant operations, reject unknown tenants on tenant endpoints, and reserve internal schema/domain names. This review does not claim demonstrated cross-tenant data reads through this behavior.
- **Abuse protection.** No application rate limiter was found for login, registration, cart, or public submissions. Form honeypots are easily bypassed. Confirm ingress/WAF limits, then add limits per IP/tenant/identity and resource bounds. Public form consent is not proof of email address ownership and must not be treated as verified login/email.
- **Sessions and tokens.** JWTs last one day; frontend logout only clears local state/cookies. Previously stolen tokens are not revoked through this logout path. Consider short-lived access tokens, revocation/rotation as needed, and BFF/HttpOnly+Secure session cookies where the architecture allows. Adding HttpOnly alone is insufficient because the frontend currently reads tokens for Authorization headers.
- **Production configuration.** Defaults include local database credentials, an HTTP API base URL, and Spring Security TRACE logging. Production needs external secrets, HTTPS, controlled log levels, production-origin CORS, and frontend security headers/CSP. Reverse proxy, TLS, and production headers were not verified in this review.
- **Dependencies.** Package/build versions were inspected for context, but no current advisory/CVE audit or registry scan was performed in this review. No claim is made that dependencies are vulnerability-free.

## Existing positive controls

- Passwords are hashed with BCrypt; JWTs use RSA signatures and have expiry times.
- Connection tenant schemas are validated and quoted; product searches use allowlisted fields and Criteria/Specification rather than concatenating SQL input.
- Tenant context is cleared in finally blocks and connection search_path is reset on release.
- MerchantOrderCreationService recalculates order prices from the catalog; client cart totals do not directly determine checkout order prices. This was therefore not reported as an order-pricing bypass.
- Theme imports bound size, depth, node count, and allowed block/section types. These controls are useful despite not sanitizing HTML/URL settings yet.
- Submission controllers expose only POST publicly; listing and deletion require authentication.
- Media replacement uses staging/backup files and transactions; read/replace paths are normalized and restricted to the storage root.
- Local runtime/JWT files are covered by gitignore rules; no tracked private key files were found in the inspected paths.

## Remediation order

1. Close public migration access and fix merchant-update/cart authorization.
2. Separate public product queries/DTOs from admin queries/DTOs.
3. Fix rich-text sanitization and URL resolution, including legacy data and theme imports.
4. Tighten upload validation and isolate the media origin.
5. Complete the role matrix, fail-closed tenant handling, abuse protection, and production configuration.

Further validation should use isolated test tenants/customers with 401/403/404 assertions, without running migrations or modifying real store data. This review did not change the application.
